# InkOS 文风分析实现解析

> 整理自源码阅读，目的：理解 InkOS 文风分析（Style Analysis）的技术实现，供在其他项目中借鉴。
> 涉及代码版本：master 分支（2026-09）。

## 0. 一句话总结

文风分析 = **一次低温度（0.3）的单轮 LLM 调用 + 以 Markdown「技能文件」形式存放的提示词工程**。产物不是模仿文本，而是一份「有证据、可执行」的文风指南 Markdown，落盘后在写作阶段作为「权威块」注入写作提示词。

## 1. 调用链路

```
StyleManager.tsx (前端页面 packages/studio/src/pages/StyleManager.tsx)
  → POST /api/v1/style/analyze          （只分析预览，不落盘，返回指南文本）
  → POST /api/v1/books/:id/style/import （绑定到书，持久化）
      → executeExplicitCapabilityTool(actionId: "generate_style_guide", risk: "recoverable-write")
        → PipelineRunner.generateStyleGuide()          packages/core/src/pipeline/runner.ts:1610
          → compileStyleGuide()  ← 核心入口              packages/core/src/agents/style-guide.ts
```

- 两个 API 端点：`packages/studio/src/api/server.ts:5908`（analyze）、`server.ts:5932`（import）。
- import 路径通过 SSE 向前端广播 `style:start / style:complete / style:error` 事件。
- **双端点设计**：无状态预览 vs 书绑定的持久化写入，是可借鉴的交互模式。

## 2. 核心函数 `compileStyleGuide`

位置：`packages/core/src/agents/style-guide.ts`（全文仅 46 行）。

```ts
export async function compileStyleGuide(input: {
  client: LLMClient;
  model: string;
  projectRoot: string;
  referenceText: string;     // 参考文本（原文整段喂入）
  sourceName?: string;       // 来源名称
  language?: "zh" | "en";
  activeSkills?: ReadonlyArray<ActivatedSkillGuidance>;
  signal?: AbortSignal;
}): Promise<string>
```

关键实现细节：

| 细节 | 说明 |
| --- | --- |
| 强制依赖两个技能 | `inkos-long-story-analysis` + `inkos-imitation-writing`，找不到直接抛错。真正的提示词工程不在代码里，而在技能 Markdown 文件里 |
| 单轮调用、无工具、无循环 | 通过 `runWorkerAgent` 跑 `tools: []` 的 worker agent。风格提取是一次性任务，不需要 agentic 循环 |
| temperature **0.3** | 分析任务低温度保证稳定；对比写作阶段 `writer.ts:138` 用 **0.7**。即「分析低温、创作高温」分工 |
| 空文本防御 | 参考文本 trim 后为空直接抛错；返回空指南也抛错 |
| 双语提示词 | system / user 提示词均按 `zh` / `en` 两套 |

### 提示词原文

**System prompt（中文）**：

```text
把参考文本编译为有证据、可执行的文风指南，只返回 Markdown。
```

**System prompt（英文）**：

```text
Compile the reference into an evidence-backed operational style guide. Return Markdown only.
```

**User prompt 模板**：

```text
来源：{sourceName}
（英文版：Source: {sourceName}）

{参考文本全文}
```

注意 system prompt 的措辞只有一句话，但每个词都是约束：
- **有证据（evidence-backed）**：要求结论附原文依据；
- **可执行（operational）**：产出的是可指导写作的指令，不是文学评论；
- **只返回 Markdown**：锁定输出形态。

## 3. 提示词工程：两个技能文件（维度清单所在）

技能 = 带 YAML frontmatter（name / description）的 Markdown 文件，由 `skills/builtin-loader.ts` 加载。

### 3.1 `inkos-long-story-analysis/SKILL.md` — 定义「分析什么」

> 长篇小说拆稿、文风分析与可迁移机制提炼。Use when analyzing a full novel or long sample without copying its expression.

要点摘录：

- 用 `ingest_material` 把来源保存为可追溯素材（文件 / PDF / URL / 上传）。
- 分析语义机制：读者承诺、冲突升级、角色动机、信息释放、场景功能、情绪回报、卷节奏、散文行为、连续性负担。
- **保留来源证据指针；把直接观察与推断分开**。
- 提取可复用的工艺（craft），而非人名、措辞、场景顺序或标志性组合。

**文风分析维度清单**（原文）：

> For style analysis, describe narrative distance and tone, dialogue behavior, scene-detail selection, transitions, sentence and paragraph rhythm, diction, emotional externalization, and distinctive habits. Anchor each important claim to a short source example.

即八个维度，每条重要论断须锚定一段原文短例：

1. 叙事距离与语气（narrative distance and tone）
2. 对话行为（dialogue behavior）
3. 场景细节选取（scene-detail selection）
4. 过渡（transitions）
5. 句子与段落节奏（sentence and paragraph rhythm）
6. 用词（diction）
7. 情绪外化（emotional externalization）
8. 标志性习惯（distinctive habits）

另外：如用户希望后续写作参考该来源，调用 `manage_book_reference(action="bind")`，绑定的是「指导」而非正典（canon）。

### 3.2 `inkos-long-story-analysis/references/analysis-lens.md` — 深层拆解透镜

仅在「完整拆解或对比」交付物时加载。**八层模型**：

| 层 | 内容 |
| --- | --- |
| Promise（承诺） | 读者期待什么样的持续阅读体验 |
| Story engine（故事引擎） | 可重复的压力-选择-后果-回报循环 |
| Structure（结构） | 开篇契约、弧线过渡、卷目标、中点变化、回报埋设 |
| Character（角色） | 欲望、恐惧、策略、关系运动、声音、不可逆选择 |
| Information（信息） | 读者 / 主角 / 对手在各阶段分别知道什么 |
| Scene craft（场景工艺） | 入场压力、具体动作、证据、转折、后果、离场张力 |
| Prose behavior（散文行为） | 视点距离、句子运动、对话潜台词、细节选取、段落节奏 |
| Long-horizon state（长程状态） | 事实、承诺、钩子、未偿代价、连续性负担 |

**输出纪律**（原文）：

> Anchor important claims to a chapter or excerpt. End with transferable principles, failure conditions, and several recombination options. Never output a disguised rewrite of the source.

即：重要论断锚定到章节或选段；以可迁移原则、失败条件、若干重组选项收尾；**永远不要输出变相改写原文**。

### 3.3 `inkos-imitation-writing/SKILL.md` — 防抄袭合同

> 从参考文本提取可迁移的文体方法，为全新故事建立可执行风格指纹。

- 用户新作的前提、角色、事实与方向仍是权威；**参考文本提供的是工艺证据（craft evidence），不是故事内容**。
- 可迁移特征清单：叙事距离、句子运动、段落节奏、对话密度、感官选取、意象行为、幽默、信息释放。
- **禁止复用**：源作人名、标志性短语、场景顺序、情节组合、可辨识段落。
- 把分析转化为**简洁的、正向指令式的**操作型文风指南，附少量源文佐证观察。
- 应用指南时要灵活，让新作读起来连贯，而不是「逐句换装（sentence-by-sentence costume）」。

## 4. 技能注入机制（最值得借鉴的工程细节）

位置：`packages/core/src/agents/base.ts:107`（`prepareWorkerMessages`）、`packages/core/src/agent/skill-tool.ts`。

### 4.1 注入格式

`appendActivatedSkillGuidance`（`base.ts:167`）把技能内容追加进 system prompt，格式：

```markdown
## Activated professional skills
Use this specialist methodology for the current operation. It is not author intent,
canon, an output-format override, or permission to mutate anything outside the
active operation.

### {skill.id} — {skill.name}
{技能正文}

#### Reference: {资源路径}:{charStart}-{charEnd} · {heading}
{资源片段正文}
```

第一句声明明确划定技能内容的**权限边界**：是专业方法论，不是作者意图、不是设定、不是输出格式覆盖、也不是越权许可。

### 4.2 引用资源的双层加载

1. **字面链接全量加载**（`skill-tool.ts:249` `loadLinkedSkillResources`）：正则扫描 SKILL.md 中的 `references/*.md|txt` 链接，把被引用文档全文带入 prompt。安全护栏：
   - `safeChildPath` 防路径逃逸；
   - 单文件大小上限（`MAX_SKILL_RESOURCE_BYTES`）；
   - 拒绝符号链接；拒绝含 `\0` 的内容（必须是纯文本）。
2. **按查询检索 top-k**（`skill-tool.ts:167` `retrieveSkillResources`）：把技能 references 目录下的 md/txt 用 `splitMarkdownForSearch` 按标题段落切块（保留 `charStart/charEnd` 偏移），写入 **SQLite FTS5** 全文索引（`retrieval/local-search.ts`），按当前任务 query 取 **top 4** 段。索引注释明确定位：「唯一的词法检索内核，源文件才是权威，数据库只是可重建的 FTS5 投影」。这样技能文档可以写得很厚，而 prompt 里只进相关部分。

### 4.3 审计与上下文预算

- **可审计**：每个被应用的技能及资源片段做 sha256 哈希，记入执行证据（`skills-applied` 事件，`base.ts:140`）。
- **上下文预算**：知道模型 contextWindow 时走 `compileContext`，预算公式：

  ```
  budgetTokens = contextWindow − maxTokens − 2048
  ```

  任务消息为 protected 优先级，技能指导 priority 0，work 元数据 priority −1。
- **authorRequest 注入**：若存在用户原始请求，会在消息最前插入一条 system 说明——委托指令可以细化但不能替换用户请求的目标或扩大变更范围。

## 5. Worker Agent 运行时（`agent/worker-agent.ts`）

- `runWorkerAgent`：包装 `@mariozechner/pi-agent-core` 的 Agent，自定义 `streamFn` 把传输统一路由到 InkOS 自己的 `chatCompletion` provider 边界——重试、上下文守卫、流超时等行为与全项目一致（Pi 只管生命周期，传输归 provider）。
- `runWorkerAgentTool`（`worker-agent.ts:312`）：需要**结构化输出**时的范式——
  - 模型必须通过唯一的 TypeBox 工具提交结果，system prompt 追加「Finish by calling {tool} exactly once. Do not print the result as prose or JSON.」；
  - `toolChoice: "required"` 强制调用工具；
  - 参数先经 `decodeStructuredFields` 容错解码，再校验，失败抛 `WORKER_SCHEMA_INVALID`；
  - 领域校验失败有界重试（最多 3 轮修正）；
  - 错误码细分：`WORKER_RESULT_INVALID` / `WORKER_RESULT_MISSING` / `MODEL_OUTPUT_LIMIT` / `WORKER_MODEL_ERROR`；
  - 原则：「宿主消费的结果绝不从 assistant 正文里抠 JSON」。
- 文风分析本身用的是纯文本版（产物是 Markdown 指南，非结构化 JSON）。

## 6. 产物落盘与消费（闭环）

1. **落盘**：`PipelineRunner.generateStyleGuide()` 把指南写到 `works/{bookId}/source/story/style_guide.md`（经 `syncWorkSourceArtifacts` 提交，可版本化 / diff）。
2. **写作时注入**：
   - `writer.ts:103`：`writeChapter` 读取 `story/style_guide.md`；
   - `writer-prompts.ts:25/34`：以 `authorityBlock("文风指南", styleGuide)` 注入 writer system prompt，与「本书规则」并列。
3. **权威顺序合同**（`writer-prompts.ts:43`，风格指南在权威链中的位置）：

   > 当前用户指令和 chapter memo 决定本章任务；既成事实、显式禁令、已选上下文和真实 hook id 必须保留。卷纲仅在无冲突时作为兜底。

   风格指南是约束之一，不是最高指令。
4. **衍生书继承**：`importCanon`（`runner.ts:1637`）把母本的 `style_guide.md` 随正典一起投影到衍生书。

## 8. 可借鉴的设计点

1. **提示词即数据**：分析逻辑放在带 frontmatter 的 Markdown 技能文件里，不改代码即可调优，且天然可哈希审计（sha256 进执行证据）。
2. **提取任务不需要 agent 循环**：单轮 + 低温度（0.3）+ 一句话强约束 system prompt（「有证据、可执行」「只返回 Markdown」）足够，省 token 且稳定。
3. **维度清单内置在提示词里**：固定的分析维度列表（八个文风维度 / 八层拆解透镜）保证不同输入下输出结构一致。
4. **证据锚定 + 观察/推断分离**：每条结论附原文短例，直接观察与推断分开——大幅提升可信度，方便人工校对。
5. **防抄袭合同独立成技能**：把「只学方法不抄表达」写成显式负面清单（禁人名 / 标志性短语 / 场景顺序 / 情节组合），外加「不要变相改写原文」的兜底——风格迁移类功能的合规底线设计。
6. **产物是中间格式而非成品**：先产出「指南」这个可版本化、可 diff、可人工编辑、可复用的中间产物，再在生成时注入——分析与应用解耦。
7. **正向指令式指南**：指南要求写成 positive instructions（怎么做），而非否定式禁令（别怎么写），对 LLM 执行更友好。
8. **技能资源的双层加载**：字面链接全量加载（确定性）+ FTS5 按查询检索 top-k（上下文经济），兼顾两头。
9. **权限边界声明**：注入技能时明确声明它「不是什么」（不是意图 / 不是正典 / 不是格式覆盖 / 不是越权许可），防止技能内容被模型过度泛化。
10. **需要结构化输出时**：用「唯一工具 + toolChoice required + 有界重试 + 细分错误码」的宿主校验范式，绝不从正文抠 JSON。
11. **分析低温、创作高温**的分工；风格指南在生成提示词中的权威链位置显式声明。
