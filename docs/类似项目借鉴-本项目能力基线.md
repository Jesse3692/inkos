## 2) 目标用户与核心任务

### 现状
- 定位:**故事创作 AI Agent 系统**,覆盖长篇小说、短篇、剧本、分镜、互动影游、开放世界(Play)与多语言翻译等 **13 类创作形态**,对外提供 Studio(Web)/ TUI / CLI 三种交互面(`README.md:6`、`README.md:27`、`运行指南.md:10`)。
- 底层四类执行者(Studio Chat、TUI、`inkos interact`、生产 worker)共用同一 pi-agent Harness:`README.md:67`「单一生产 Harness:Studio Chat、TUI、`inkos interact` 与生产 worker 共用 pi-agent 工具循环和结构化 action/result」;注意 `运行指南.md:10` 只表述三种交互面,「四入口共用」的依据在 `README.md:67`。
- 核心能力 = 统一 Harness 上的 **10 个 capability**(workspace/longform/short-fiction/script/storyboard/interactive-film/interactive-world/translation/adaptation/visual),`packages/core/src/harness/production-capabilities.ts:208-428` 中 `registerToolCapability` 共 10 处注册(撰写人实测该文件含 12 处字符串,其中 10 处为 capability 注册、1 处为 :175 嵌套注册、1 处为 :464 函数定义);9 个 Work Profile 经 capabilityIds 映射到这些能力(`packages/core/src/harness/builtin-profiles.ts:5-72`)。
- 用户最常完成的三个任务(README 快速开始即最小主链路):**建书 + 逐章写作**(`README.md:297-306`)、**审稿/修订**(`README.md:295` 命令清单、`packages/cli/src/commands/review.ts:5-12`)、**导出交付**(`packages/cli/src/commands/export.ts:6-11`;短篇整包 + 封面见 `README.md:308-325`)。

## 3) 端到端流程图(现状)

### 现状(三条主链路 + 专项)

**链路 A:长篇(建书 → 逐章 → 审稿 → 导出)**

3. 模型服务配置(创作前必做):`inkos config set/set-model`(`packages/cli/src/commands/config.ts`)→ `packages/core/src/llm/service-resolver.ts`、`llm/api-format.ts`。
4. 逐章写作 `inkos write next`(`packages/cli/src/commands/write.ts:64-75`)→ PipelineRunner(`packages/core/src/pipeline/runner.ts:1292-1440`):
   `prepareWriteInput` → Planner(落盘 `chapter-XXXX.intent.md`,`packages/core/src/agents/planner.ts:103-108`)→ Composer(落盘 `context.json`/`trace.json`,`composer.ts:147` → `utils/runtime-writer.ts:22-23`)→ Writer 起稿(`runner.ts:1326`)**并在其阶段 2 提交 typed delta**(`packages/core/src/agents/writer.ts:163-180`)→ ContinuityAuditor 审稿(`runner.ts:1341`)→ 若正文被改动则再结算(`runner.ts:1870-1883`)→ StateValidator 对账(`runner.ts:1394` → `pipeline/chapter-truth-validation.ts:44-53`)→ 原子落盘(`writer.ts:392-450`:`chapters/XXXX.md` + story 投影 + `story/state/*.json` + `story/snapshots/N/` + `chapters/index.json`)。

## 5) 文本切块策略

### 现状
- **创作链路:以「章」为唯一切块单位**,不做段落级切分(`packages/core/src/utils/chapter-splitter.ts:6-8`:`SplitChapter{title,content}` 接口 + 编号标题正则),相邻块不重叠(块即章,无 overlap 概念)。
- **上下文不是固定 token 窗口,而是「段 + 条目」分级**:protected(章节 memo、current_focus、author_intent、style_guide、parent_canon、fanfic_canon、大纲段、当前状态事实、角色卡、memo 引用伏笔)与 compressible(历史摘要、卷摘要、hook 检索结果)两类(`packages/core/src/harness/context-compiler.ts:4`、`:112-114`);protected 超预算直接抛 `ProtectedContextOverflowError` 而非静默截断(`context-compiler.ts:71-72`)。
- compressible 交 LLM 做语义编译,不接受 protected 片段(`packages/core/src/agents/semantic-context-compiler.ts:19-84`、`:20-21`)。
- **token 估算**:CJK 每字 1、非 CJK 每 4 字符 1(`packages/core/src/llm/provider.ts:539-544`);单行超预算用二分按字符硬切(`packages/core/src/llm/semantic-input.ts:15-61`)。
- **记忆候选池**:BM25 `limit: 200`,未命中项以 `score: -1_000_000` 兜底进池(`packages/core/src/utils/memory-retrieval.ts:95-104`)。
- **导入/翻译链路存在二次切分**:翻译按 `maxChars = 1200` 分段(`packages/core/src/translation/text.ts:30-42`);长文续写在输出上限处最多续写 3 次(`packages/core/src/llm/long-form-completion.ts:16-49`,`:24` `maxContinuations ?? 3`)。
- **变更区域计算**:单侧截断 2000 字符并标记 `truncated`(`packages/core/src/utils/source-text.ts:31-38`)。

> **复核修正(板块三·清单 4-5)**:**「不做段落级切分」仅对创作链路成立**;翻译/导入链路确有段落与字符级二次切分,引用时须加此限定。

### 对照清单的缺口
- 无语义切块(按句/段 embedding 边界切分)、无跨章重叠窗口、无按需自适应窗口。
- 超长章无结构感知分段(仅靠长文续写兜底),场景边界不参与切块决策。
- 压缩是「整段交 LLM 语义编译」,非分层摘要(句→段→章),压缩结果不可分层回查。
- 章节正文本身不进检索索引,跨章细粒度召回只能依赖章节摘要;只有上一章正文会整篇注入(且只给 Planner,不给 Writer)。

### 建议借鉴方向
- 把语义切块 + 重叠窗口做成可选项(默认仍章级),对超长章按场景边界分段。
- 压缩改分层(句→段→章)并保留指针,使「哪一句被压掉了」可追溯。

## 6) Prompt 设计方法

### 现状

按清单第 5 项的八个子问题逐条回答:

1. **分几个阶段**:长篇为多阶段链——地基 4 步(故事框架/卷纲 `packages/core/src/agents/architect.ts:269-282`;开篇人物索引 `architect.ts:319-322`;角色卡 `architect.ts:326-332`)→ Planner 章节意图 → Composer 上下文包 → Writer 正文(`packages/core/src/agents/writer.ts:327`)→ 审稿(`packages/core/src/agents/continuity.ts:40-42`)→ 修订 → Settler 状态投影(`packages/core/src/agents/settler-prompts.ts:14-17`)→ StateValidator 对账;另叠加 Harness 主 Agent 系统提示(`packages/core/src/harness/system-prompt.ts`)与 20 个 `SKILL.md` 正文。
2. **每阶段解决什么**:地基产出可读故事框架与卷纲;Planner 产出章节意图;Composer 产出受治理上下文包(裁剪);Writer 产出正文;Auditor 产出观察;Settler 产出增量 truth;Validator 做一致性对账(宿主确定性执行)。
3. **输入材料如何裁剪**:protected/compressible 分级 + protected 超预算即错(`packages/core/src/harness/context-compiler.ts:4`、`:71-72`、`:112-114`);compressible 交 LLM 语义编译(`packages/core/src/agents/semantic-context-compiler.ts:20-21`);token 估算(`packages/core/src/llm/provider.ts:539-544`);记忆候选池 limit 200(`packages/core/src/utils/memory-retrieval.ts:95-98`);导入/翻译 `maxChars 1200`(`packages/core/src/translation/text.ts:30-42`);变更区域单侧 2000 字符(`packages/core/src/utils/source-text.ts:31-38`)。
4. **输出约束如何定义**:全部走结构化结果工具(`submitStructured` + Zod/TypeBox schema)。例:审稿四态枚举 `issue/resolved/observation/unavailable` + `categoryRequired`(`packages/core/src/agents/review-tool.ts:12-20`);Settler 的 typed delta(`packages/core/src/agents/settler-tool.ts:43-49`,factOps upsert/expire + hookOps);人物索引只允许 `{tier,name}` 两字段且禁止把无名岗位扩写成传记(`architect.ts:319-322`)。
5. **如何禁编造 / 要求 evidence / 处理不确定信息**:审稿必须提交编号原文证据行(`continuity.ts:41`),宿主按行号回填原文并校验一致性(`packages/core/src/models/observation.ts:28-67`,quote 与源不符抛 `REVIEW_SOURCE_MISMATCH`,缺引用抛 `REVIEW_SOURCE_REQUIRED`);证据缺失用 `assessment="unavailable"` 表达,并明示「missing evidence is not a content defect」(`review-tool.ts:14`);地基阶段「压缩资料包是证据,不是臆造缺失正典的许可」(`architect.ts:216-217`);Settler「不把计划当成已发生事件」(`settler-prompts.ts:16`);状态投影 Skill「大纲材料是计划上下文,不是事件已发生的证据」(`packages/core/skills/inkos-long-writing/references/state-projection.md:9`);同人 Skill「do not turn a guess into canon」(`packages/core/skills/inkos-fanfic-writing/SKILL.md:11`);违规引用被拒并附修正指令(`observation.ts:60-67`)。
6. **是否区分观察与推断**:**审稿层区分**——`assessment` 四态 + `category`(execution/quality/scope)(`review-tool.ts:14-20`、`packages/core/src/models/observation.ts:8-9`);**状态层不区分**——`CurrentStateFact` 只有 subject/predicate/object/validFrom/validUntil/sourceChapter,无 provenance 与 confidence 字段(`packages/core/src/models/runtime-state.ts:58-65`),即观察与推断的区分止步于审稿,未进入 runtime state。
7. **是否限制输出数量**:maxTokens 逐阶段设定(地基 8192/2048/8192,`architect.ts:282`、`:320`、`:332`;审稿 ≤4096,`continuity.ts:89`;正文 ≤16384,`writer.ts:327`);observations 可为空且明示「空数组是合法结果」(`continuity.ts:42`);issues 上报截断至 16 条并提示撤回无依据项(`observation.ts:62-67`);长文续写最多 3 次(`packages/core/src/llm/long-form-completion.ts:24`)。
8. **prompt 修改后缓存如何失效**:无 provider 级 prompt cache(全仓 `cache_control|anthropic-beta|prompt cache` 在 `.ts` 源码零命中,构建产物内命中已人工排除);应用层 Agent 缓存按 17 个字段比对失效(`packages/core/src/agent/agent-session.ts:874-913`),skill 解析结果进 sha256 key(`agent-session.ts:315-349`),profile JSON 也进 key(`agent-session.ts:859`),TTL 5 分钟(`agent-session.ts:250`)。因此改 `SKILL.md` 或 prompts 字面量都会改变缓存 key → 缓存失效;**但 prompt/skill 版本不随产物落盘,无法从产物反查 prompt 版本**(见 §7 修正②)。

### 对照清单的缺口
- 无 prompt 版本管理:prompt 不是带版本的工件,改动无评分保障、无回归。
- 无 prompt A/B、无 prompt lint;systemPrompt 组装分散在 20+ 文件,无单一注册表。
- 「证据强制」只在审稿阶段实现,Writer/Settler 的事实输出没有同类 host 回填校验。

### 建议借鉴方向
- prompt 内容寻址 + 版本号随产物落盘,使「模型 + prompt 版本 + 输入证据行」可反查。
- 把「host 回填 + 一致性校验」模式推广到所有事实性输出阶段;prompt 变更接入 golden 回归(见 §22 P1 第 5 条)。

- evidence 机制只覆盖**审稿观察与素材/skill 证据**,不进入长篇 runtime state(facts 只有 sourceChapter,无 evidence 字段)。

## 11) 场景状态、世界状态与角色知识边界

### 现状

## 20) 暂不适用的清单项(说明为何不适用)

### 现状
判定标准:清单明确问到、但按本项目当前定位与架构决策确实不需要(或仅边缘适用)的项。与「真实缺口」严格区分——易被误列为不适用但实为缺口的(大规模性能实测、向量检索、golden dataset、prompt 版本记录、场景级状态等)归入 §15/§19,不在此列。当前定位:单机本地创作工具 + 「角色是创作产物而非运行时 Agent」的确定性创作管线。

### 对照清单的缺口(不适用判定)

2. **多租户认证 / 按用户限流 / 水平扩展**:InkOS 是单机本地创作工具(默认 127.0.0.1,唯一边界是 loopback 的 Host/Origin 白名单,`packages/studio/src/api/server.ts:2605-2621`),单用户使用;清单中的「多作品隔离」已由 `works/<id>` 目录 + 每 Work 文件锁 + WAL sqlite 覆盖(`state/manager.ts:129-213`、`harness/episode-store.ts:27-29`),租户级配额与节流暂无适用场景。**与 §19 第 11 条的边界**:多租户认证、按用户限流、水平扩展在此列(暂不适用);**单用户非 loopback 绑定的基础认证**(口令/token)属部署安全基线,归入 §19 第 11 条(在范围内)。**边界条件**:若推出托管多用户服务,认证/限流/隔离模型需整体重做。
3. **对话式产品的「重复回复/复读检测」作为独立子系统**:长篇的重复问题由审稿观察 + `revise --mode anti-detect` + `inkos-story-deslop` Skill 覆盖(`README.md:367`),不存在对话轮次的复读场景;并入第 1 项的多角色调度边界内评估。

### 建议借鉴方向
- 对每一项「不适用」记录其**定位假设**:一旦假设变化(Play 演进为多 NPC 自主社交、推出托管多用户服务),对应能力须重新纳入评估——建议在 spec 中以「触发条件」形式固化,避免能力边界被静默漂移。

## 22) 建议优先级和验收方式
